# Обзор и анализ репозитория LS (GhostGPT / LCS)

Дата: 2026-03-12

## 1) Executive summary

Репозиторий выглядит как **крупный мультистековый монорепо** (Python + Rust + web-frontend + Android-черновик) с сильной исследовательской компонентой, но с признаками «археологии» и неоднородности поколений кода.

**Сильные стороны:**
- Чётко заявленная архитектура LCS/GhostGPT и позиционирование в README.
- Наличие Rust-ядра и CI-пайплайнов под разные области.
- Существенное покрытие unit-тестами (локально запускаются сотни тестов).

**Ключевые риски:**
- Дублирование и рассинхрон модулей (например, `agent/` vs `python/modules/agent/`).
- Технический долг в import-слое (обёртки с self/circular import).
- Smoke-тесты не проходят на этапе collection из-за структуры импортов и зависимостей.
- В рабочем дереве присутствуют тяжёлые артефакты (`node_modules`, `.gradle`), что создаёт риск случайного «шумного» коммита.

## 2) Что видно по структуре

Репозиторий сочетает несколько подсистем:
- `python/modules/*` — основной Python-стек (agent, llm, shared, web4_runtime и др.).
- `rust_core/*` и `ncafuzzycore/*` — Rust-компоненты.
- `ghostgpt-ls-landing/*` — frontend-лендинг (Vite/Tailwind).
- `apps/*` — точки входа приложений, включая `console`, `ghostgpt`, `android`.
- `tests/*` и `python/tests/*` — тестовые наборы.

По tracked-файлам видно доминирование Python (`~572 .py`) при заметной документационной и инфраструктурной доле (`~155 .md`, workflow, Rust-часть).

## 3) Архитектурная зрелость: плюсы

1. **Хорошо оформленная продуктовая рамка** в README (LCS, 12-слойная архитектура, local-first, Rust acceleration).
2. **CI-практики присутствуют**: отдельные workflow для security/CI и Web4 runtime.
3. **Фокус на качестве/безопасности в CI**: lint/type-check/test, dependency audit, SBOM, CodeQL.
4. **Тестовая база большая**: unit-набор локально отрабатывает в объёме 200+ кейсов (хоть и не полностью зелёный).

## 4) Главные проблемы, выявленные при проверке

### 4.1 Импортная архитектура и дублирование пакетов

Обнаружен паттерн «обёртки-переэкспорта», который ведёт к циклам импортов. Пример:

- `python/modules/agent/counterfactual_engine.py` импортирует `CounterfactualEngine` из `agent.counterfactual_engine`.
- При этом в корневом `agent/counterfactual_engine.py` находится фактическая реализация.

Такой дизайн хрупок и уже проявляется в smoke-тестах как circular import.

### 4.2 Smoke-тесты не проходят (проблема воспроизводимости)

`tests/smoke` падает на collection:
- `ModuleNotFoundError` (`agent.loop`, `agent.event_schema`),
- `ImportError` (relative import beyond top-level package),
- отсутствие обязательной зависимости `yaml` (PyYAML) в текущем окружении.

Это указывает на несогласованность package-layout и PYTHONPATH-стратегии между тестами и рабочим кодом.

### 4.3 Unit-тесты частично красные по бизнес-логике

Локально: `224 passed, 4 failed, 2 skipped`.
Падения не инфраструктурные, а семантические:
- ожидался `BlockReason.THREAT`, получен `BlockReason.OVERLOAD`;
- ожидалась перераспределённая attention-модель (`light > 1.0`), фактически ниже;
- рассинхрон ключей метрик (`collective_initiative` отсутствует).

Это похоже на регрессию контрактов после изменений в моделях/метриках.

### 4.4 Конфигурационная и историческая «смешанность»

Есть признаки нескольких исторических слоёв проекта:
- `project_status.py` ожидает файлы вроде `main.py`, `config.py`, `llm_module.py` в корне, что не отражает актуальную структуру.
- README описывает актуальные и неактуальные пути одновременно (эволюция не полностью «зачищена»).

## 5) CI/CD и инженерная дисциплина

### Что хорошо
- Есть отдельные workflow для security и для Web4-ветки.
- Используются проверенные практики: pytest, ruff, mypy, pip-audit, cyclonedx, CodeQL.

### Что улучшить
- Свести к единой стратегии import/package (editable install + единый PYTHONPATH policy).
- Добавить «быстрый contract smoke» в pre-merge с валидацией критичных импортов.
- Явно отделить legacy-скрипты (архив/legacy папка), чтобы не вводить в заблуждение.

## 6) Рекомендации (приоритетный план)

### P0 (сразу)
1. Убрать циклические re-export import-цепочки в `python/modules/agent/*`.
2. Зафиксировать единый способ запуска тестов и импорта модулей (через пакетное имя, без двойных корней).
3. Привести smoke-тесты к зелёному collection (минимум).
4. Добавить `.gitignore`-политику/проверку против случайного попадания `node_modules` и `.gradle` в PR.

### P1 (короткий спринт)
1. Синхронизировать доменные контракты, из-за которых падают 4 unit-теста.
2. Актуализировать/архивировать legacy-утилиты (`project_status.py` и подобные).
3. Сформировать карту ownership по директориям (кто владеет каким контуром).

### P2 (дальше)
1. Ввести архитектурные ADR по package boundaries.
2. Добавить интеграционный «repo health dashboard» (импорты, тесты, типы, критичные метрики).

## 7) Быстрый вывод

Проект технически мощный и амбициозный, с хорошим заделом на production-grade практики, но сейчас ограничен **структурным техдолгом в модульной организации**. При фокусе на устранении import-архитектуры и контрактных рассинхронов качество и скорость разработки можно заметно повысить без смены технологического стека.
